# Plan: 03-02 (Integrate PDF returning mechanism and memory/zombie safeguards)

## Objective
Read the compiled PDF back into the Rust process and send it as a byte array to the frontend. Implement safeguards so `pdflatex` processes do not become zombies. Integrate the frontend adapter to call the Tauri backend.

## Tasks
1. **Read PDF Buffer and Logs**:
   - In `compile_latex` (in `main.rs`), after the process finishes:
     - Check if `document.pdf` exists. If so, read it using `std::fs::read` and return it in `pdf_buffer`.
     - Read `document.log` and include it in `log`.
   - Ensure the temporary directory is dropped and deleted even on failure. Rust's `tempfile::TempDir` does this automatically on drop, but we must not leak references.
2. **Handle Frontend Integration**:
   - Update `public/backend-adapter.js`.
   - In `invokeCompile(latexCode)`, implement the `isTauri` branch:
     - Use `window.__TAURI__.core.invoke('compile_latex', { code: latexCode })`.
     - Map the response: `pdf_buffer` needs to be converted into an ArrayBuffer since Tauri sends `Vec<u8>` as an array of numbers. Convert `data.pdf_buffer` using `new Uint8Array(data.pdf_buffer).buffer` and return it.
     - Return `{ pdfBuffer: ..., log: data.log }` matching the expected frontend API.
3. **Zombie Safeguards**:
   - Instead of a simple `wait()`, use a timeout or kill the child process if it runs for more than 5 seconds. (Since `std::process::Command` is synchronous, we'll wrap it or use `Child::wait` properly; for a true timeout we can poll or use a thread, but for now `-halt-on-error` should prevent hanging. We will ensure the child is killed if it's still running).
